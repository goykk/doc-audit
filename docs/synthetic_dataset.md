# 合成中文发票数据集 v1

生成脚本：`scripts/make_synthetic_invoices.py`（可重复生成，图片不进库）
标签：`data/ground_truth/synthetic_labels.jsonl`
标准答案：`data/ground_truth/synthetic/syn_invoice_*.json`

全部为合成数据，票面带“合成测试数据，不具备法律效力”字样，不含任何真实票据信息。

## 构成

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| 干净发票 | 38 | 字段自洽，预期 accepted |
| 单故障发票 | 10 | 每张只注入一个已知业务错误 |
| 重复票 | 2 | 与干净票 0001 同票号，一张金额相同、一张金额不同 |
| 合计 | 50 | 覆盖 R001~R013 |

R014（置信度）不通过文档注入，由 `tests/test_validation.py` 单测覆盖。

## 故障覆盖

| 规则 | 注入方式 |
| --- | --- |
| R001 | 价税合计比“不含税+税额”多 60 |
| R002 | 大写金额改成固定错误值 |
| R003 | 第二行金额 +10，小计不变 |
| R004 | 税率印 13%，税额仍按 6% |
| R005 | 购方税号改成 5 位 |
| R006 | 开票日期改为未来 30 天 |
| R007 | 第一行单价打八折，行金额不变 |
| R008 | 价税合计（小写/大写）比实付合计多 20 |
| R009 | 发票号码改成 `A12` |
| R011 | 第一行数量、单价改为负数，行金额保持正数 |
| R012 | 0021 与 0001 票号、金额、行项目完全相同 |
| R013 | 0022 与 0001 同票号但金额不同 |

## E3 结果

### Oracle 模式（标准答案直接进校验器）

- 故障拦截：12 / 12（100%）
- 期望规则命中：12 / 12（100%）
- 干净文档误报：0 / 37（0%）
- 自动通过率 74.00%，复核工作量 26.00%

这一模式只证明规则实现正确，不代表真实链路的召回。故障是按规则形态构造的，存在“为规则量身定做”的偏差。

### Pipeline 模式（qwen3-vl-plus 真实抽取 → 校验）

- 字段级 F1：0.9980，行项目整单准确率 100%
- 故障拦截：11 / 12（91.67%）
- 期望规则命中：10 / 12（83.33%）
- 干净文档误报：0 / 37（0%）
- 自动通过率 76.00%，复核工作量 24.00%

两张未按预期命中的原因：

1. `syn_invoice_0018`：VLM 把“价税合计”读成了“实付合计”，抹平了原始差异，最终由 R002 大写金额不一致拦住，规则命中错位但文档仍被拦截。
2. `syn_invoice_0019`：票面发票号是非法值 `A12`，VLM 用发票代码 `011002600111` 替换了它。替换后的号码合法，R009 不触发，文档被自动通过。

第 2 条是这套系统最重要的边界：**当模型“自作聪明地修正”了错误值时，规则层无法发现，因为错误已经不在数据里了。** 这类风险只能靠低置信度、原文证据比对或抽样人工复核兜底。
